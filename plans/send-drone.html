Send a drone from the monitor

The Sites monitor we already have, with one addition: open a camera, see a box on every person with Sauron's real suspicion, click Send drone on one, and the drone launches to that person.

1 camera usable: jetson-c920 dispatch code not deployed no person boxes in the UI yet drone flies to the point, does not follow yet

What changes on screen

Nothing else in the monitor changes. The addition lives in the camera lightbox (the view you get by clicking a camera tile twice).

  • Live view: a ring frame from the Jetson about once a second, with the edge YOLO person boxes from that exact moment drawn over it. The picture runs about 2.5–3 s behind live, and the screen says so.
  • Label on each box: the person Jev pointed at in an open incident shows its verdict colour, reason, E, top facts and caption. Every other box shows —. Jev scores a clip and picks one subject; there is no per-person score, so we don't invent one. With the judge off, all boxes show — and a "judge off" banner.
  • Send drone: an inline "Send drone to #id? Yes / Cancel", then the new incident opens in the left pane (queue, Forwarded, map pin) and the chip turns red.
  • Abort drone: a button on an open, forwarded incident in the left pane. The API already exists; without the button the only recall is waiting for the person to leave view.

The click is an extra trigger. Sauron's own launches stay autonomous with no approval step. If both fire on the same person, the drone takes the first and refuses the second as busy.

What a click sends

POST /ask/api/dispatch/launch          (internal login, audited)
{"camera_id": "jetson-c920", "track_uuid": "<box.track_uuid>", "t_ns": <frame time>}

200 {"id": "jetson-c920-op-…", "located": true, "lat": …, "lon": …,
     "loc_source": "sitefuse", "site_track_id": "…", "already_dispatched": false}
409 "person no longer tracked" | "no dispatch webhook is configured"

The server builds a live deploy incident with reason operator_launch, grabs the frame and crop, and hands it to the existing store.accept. That binds the person to their site track, takes the location from sitefuse now (which absorbs the 2–3 s display lag), signs and sends netra.dispatch.incident, and starts the 1 Hz position stream. A small loop closes it as subject_lost when the person is gone 30 s, which sends end to the drone.

Decisions for William

  1. Camera. jetson-c920 is the only camera that is both live and calibrated (8.7 m error). It's the desk test rig. Demo on it with a "test rig" label, or no live demo. The Axis has had RTSP refused for 2+ days and is uncalibrated; node3 is offline.
  2. Deploy the droplet to main now. With no webhook URL set, nothing is sent; it creates the tables and endpoints.
  3. How the droplet reaches dwone. The tailnet ACL lets the droplet SSH to the Jetson only. Either open flywheel-01 → dwone:8765 or give sauron_link a public HTTPS endpoint.
  4. Jetson memory (optional). Stopping the two dead edge units (Axis, node3; 0 frames for days) frees about 1.9 GB for the judge.

Rehearsal order

  1. Deploy; send a signed test incident from the droplet to sauron_link; see the goal arrive in SITL.
  2. Open Camera 1 with someone on the walkway: boxes line up, lag reads ≤ 3 s. Stage people on the walkway or road, not the far field (10–40 px tall there).
  3. Click Send drone → incident with loc_source=sitefuse → forwarded 2xx → SITL drone takes off → positions streaming. Measure click-to-drone time; it has never been measured.
  4. Abort → end reaches SITL.
  5. Start the judge, stage a bike-tampering break-in: the box turns amber/red with real facts and launches with no click.
  6. Person walks out of view → incident closes subject_lost within about 30 s and sends end.
